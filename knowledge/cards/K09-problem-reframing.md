# K09 — Permit a design solution to refine the problem definition

**Knowledge type:** QUALITATIVE_RESEARCH  
**Source IDs:** DC2  
**Verification level:** SOURCE-IDENTITY + PUBLISHER/INSTITUTION ABSTRACT (or OFFICIAL NORMATIVE TEXT for WCAG). Full paper review is **not** claimed.  
**Verified claim IDs:** VC09

## When to retrieve
The requested widget is a solution guess rather than an articulation of user need.

## Verified source findings and study scope
- **Evidence — DC2 (university metadata/abstract):** Dorst & Cross analyzed design protocols from nine experienced industrial designers, discussing co-evolution of problem and solution spaces.
- **Scope:** Small, context-specific protocol research; a useful account of reasoning, not proof that every brief must be challenged.

## Transferable reasoning moves — *derived design advice, not direct experimental findings*
1. Preserve explicit requirements while marking speculative assumptions separately.
2. Generate a provisional artifact, ask what it reveals about the underlying task, then revise the definition if evidence supports it.
3. Keep a log of what changed and why; avoid inventing a different product than the user requested.

## Countercases and overclaim guard
- Explicitly review source-specific constraints in `knowledge/claims.json` and source access levels in `knowledge/sources.json`.
- Do not turn a studied observation into a mandatory style rule, numerical CSS constant, or general guarantee of user performance.
- The agent must not assert that this study validated AI-generated UI, unless such testing exists elsewhere.

## Verification in a live design
Validate the revised problem framing against actual task context and user constraints, not design intuition alone.
